3. Signal worth writing about today

The monorepo documentation gap has a mechanical fix that nobody's actually shown working

The 2026-08-06 post argued that TypeDoc's dedicated packages mode still asks a lot of a monorepo owner — per-package config duplication via packageOptions, no inheritance from the root, cross-package reference friction. That post was a comparison and critique. It didn't show the alternative actually running. Today's research reconfirms the underlying trend (Turborepo/pnpm workspaces now the default monorepo substrate, documentation still bolted on separately in most 2026 writeups) and surfaces the specific mechanism worth demonstrating: generateSite(inputPaths, options), jsdoc-scribe's own programmatic API export (require("jsdoc-scribe/docs")), already accepts an array of input paths and returns one merged set of rendered pages — which is exactly the shape needed to point it at every packages/* workspace member and get one docs site out, no per-package config file, no root-inheritance problem to work around because there's no per-package config in the first place.

jsdoc-scribe's own repo is a real, non-hypothetical example: it's an npm workspaces monorepo itself ("workspaces": ["packages/*"], member package packages/eslint-plugin-jsdoc-scribe), and its own package.json already runs gen-docs lib bin packages/eslint-plugin-jsdoc-scribe --quality --out docs-internal as a script — proof the multi-path pattern already works in production, just never shown as a copy-pasteable standalone script using the programmatic API directly. That's the angle: a worked, runnable Node script any workspaces-based project can copy, not a new feature claim.
